# Database: SQLite + PostgreSQL

LingoFlow supports two database backends behind one abstraction. SQLite remains the
default for local development and the test suite; PostgreSQL (Neon) is available for
hosted deployment. There is a single copy of every query.

> Supersedes the earlier `PostgressSQL-migration.md`, which proposed a full cutover to
> Kysely with no SQLite fallback.

## Driver selection

`server/src/db/driver.ts` resolves the dialect on first use (not at require time, so
dotenv ordering does not matter):

1. `LINGOFLOW_DB_DRIVER=sqlite|postgres` — explicit override.
2. Otherwise `DATABASE_URL` present → Postgres, absent → SQLite.

Driver modules are required lazily, so a Postgres deployment never loads
`better-sqlite3` (native binaries) and a SQLite run never needs `pg`.

## Layout

```
server/src/db.ts              All queries and schema. Dialect-neutral SQL, ? placeholders.
server/src/db/driver.ts       Factory + a better-sqlite3-shaped facade (prepare/exec/transaction).
server/src/db/sqliteDriver.ts better-sqlite3, with a prepared-statement cache.
server/src/db/postgresDriver.ts  node-postgres Pool.
server/src/db/dialect.ts      SQL translation and ? -> $1..$n rewriting.
```

`db.ts` still calls `db.prepare(sql).get(...)`, `db.exec(sql)` and `db.transaction(fn)`
exactly as it did against better-sqlite3 — the facade preserves that shape. The only
difference is that every call is now awaited.

## What the dialect layer handles

| SQLite | Postgres |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` |
| `CURRENT_TIMESTAMP` (into TEXT columns) | `to_char(now() AT TIME ZONE 'utc', 'YYYY-MM-DD HH24:MI:SS')` |
| `?` placeholders | `$1..$n` |
| `PRAGMA table_info(x)` | `information_schema.columns`, via `driver.columnInfo()` |
| `sqlite_master` | `information_schema.tables`, via `driver.tableExists()` |

The timestamp default is not cosmetic: every timestamp column in this schema is `TEXT`
and several queries compare those values lexically (`expires_at < ?`), so Postgres has
to produce the same `YYYY-MM-DD HH:MM:SS` rendering SQLite does.

`pg` returns `BIGINT` and `NUMERIC` as strings to protect precision. Every `COUNT()`
and `SUM()` in `db.ts` feeds XP, streak and accuracy arithmetic, so `postgresDriver.ts`
registers type parsers that narrow both to JS numbers.

## What was written portably instead of translated

These were rewritten once in `db.ts` into a form both dialects accept, rather than
being branched on at runtime:

- `INSERT OR IGNORE` → `INSERT ... ON CONFLICT (...) DO NOTHING`
- `lastInsertRowid` → `RETURNING id` (SQLite has supported `RETURNING` since 3.35)
- `DATE('now', '-N days')` → the cutoff date is computed in JS and bound as a parameter
- `DATE(text_column)` → `substr(column, 1, 10)`
- `HAVING attempts > 0` → `HAVING COUNT(1) > 0` (Postgres rejects output aliases in `HAVING`)
- In `ON CONFLICT ... DO UPDATE SET`, the right-hand side must **qualify the target
  column with the table name** — `xp = daily_xp.xp + excluded.xp`, not
  `xp = xp + excluded.xp`. SQLite resolves the bare name to the target row; Postgres
  reports it as ambiguous against the `excluded` pseudo-table (error 42702).
- `MAX(a, b)` → a `CASE` expression. SQLite's two-argument `MAX`/`MIN` are scalar
  functions; in Postgres those names are aggregates and the scalar equivalents are
  `GREATEST`/`LEAST`, which SQLite does not have. `CASE` is the only form both accept.
- `ORDER BY <nullable column>` states `NULLS FIRST` / `NULLS LAST` explicitly. The
  defaults are opposite — SQLite sorts NULLs first in `ASC`, Postgres sorts them last —
  so an implicit ordering silently changes which rows a `LIMIT` keeps. Only
  `item_progress.next_due_date` is affected today.

### Identity sequences

Inserting a row with an explicit `id` does not advance a Postgres identity sequence,
so any code path that supplies its own id must resync afterwards or the next generated
id collides. `seedDefaultUser()` inserts the local user as id 1 and calls
`resyncUsersSequence()` for exactly this reason — without it, the first real
registration against a fresh Postgres database fails with a duplicate key error on
`users_pkey`. `scripts/import-sqlite-to-postgres.ts` does the same resync for every
imported table. SQLite's `AUTOINCREMENT` tracks `MAX(id)` itself and needs none of this.

Booleans stay as `INTEGER` 0/1 on both backends. Several queries do `SUM(correct)` and
divide by it, so promoting them to a real `boolean` type would break arithmetic.

## Transactions

Transaction bodies call sibling functions rather than threading a handle — most visibly
`routes/sessionRoutes.ts`, where one `runInTransaction` wraps about ten exported
database functions. On Postgres every statement in a transaction must run on the same
pooled client, so `postgresDriver` puts the checked-out client in an `AsyncLocalStorage`
and `all/get/run` pick it up ambiently. Nested transactions become savepoints on both
backends.

The SQLite driver also drives `BEGIN`/`COMMIT`/`ROLLBACK` manually, because
better-sqlite3's own `db.transaction()` only accepts synchronous callbacks.

## Batched writes

Two startup routines write a row per content item. Sequentially that is free on local
SQLite and costs a network round-trip each against Neon, which made the server take
about a minute to become ready. Both now write in chunks through
`upsertWordTranslations()` and `upsertContentFingerprints()`:

| Startup phase | Before | After |
|---|---|---|
| `rebuildContentWordTranslations` | ~1047 queries | 4 queries |
| `reconcileContentFingerprints` | 113 queries | 2 queries |

Total Neon startup went from ~60s to ~10s. Note that a single `INSERT ... ON CONFLICT`
cannot touch the same conflicting row twice, so both helpers de-duplicate their input
before building the statement.

The remaining ~7s is `initSchema()`, most of it `bootstrapLanguageProgress()`, which
recomputes `language_progress` from `session_history` for every user on every boot.
That is pre-existing behaviour and is instant on SQLite, but it scales with
users × languages in round-trips — worth revisiting if the user count grows.

## Startup

Schema creation and migrations used to run as import side effects of `db.ts`. They are
now an awaited bootstrap: `database.initSchema()`, called from `initDatabase()` in
`server/src/index.ts` before the server listens. `createApp()` is async and awaits it.
Both are idempotent, so repeated calls share one run.

Tests call `initTestDb()` from `__tests__/helpers/testDb.ts` in a `before` hook.

## Migrations

There is no versioned migration runner. Schema setup is idempotent by construction —
`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and `ensure*Columns()`
helpers that add missing columns after checking `driver.columnInfo()`. Six columns
exist only as those conditional `ALTER`s and appear in no `CREATE TABLE`
(`settings.speech_rate`, `language_progress.speed_match_highscore`,
`item_progress.flashcard_known`, `community_exercises.reviewer_comment` /
`reviewed_by` / `reviewed_at`, `word_translations.source`), which is why the schema is
generated from these functions rather than from a hand-written baseline `.sql` file.

Three legacy migrations are SQLite-only and gated on the dialect —
`migrateLegacySingleUserSchema()`, the `story_completions` rebuild, and
`maybeMigrateLegacyJson()`. They are rename-copy-drop workarounds for SQLite's
inability to alter constraints, and a Postgres database is always created fresh here.

## Testing against Postgres

`npm run test` runs the suite against SQLite. That is fast and offline, but it cannot
catch dialect bugs, because the things Postgres rejects are the things SQLite accepts.
To run the same 123 server tests against Postgres:

```bash
npm run test:server:pg    # needs DATABASE_URL in server/.env
```

Each test file creates its own Postgres schema and drops it afterwards, so files stay
isolated from each other and never touch `public` — pointing this at the same database
the app uses is safe. Files run serially to keep connection count low. The schema is
applied as a connection `search_path`, which Neon's *pooled* endpoint rejects as an
unsupported startup parameter, so the harness rewrites the host to the direct endpoint.

Run this after any change to SQL in `db.ts`. It is what found the identity-sequence bug
described above, which a SQLite run passes cleanly.

## Importing SQLite data into Postgres

```bash
npm run db:import-sqlite                       # from server/data/lingoflow.db
npm run db:import-sqlite -- --from ./backup.db
npm run db:import-sqlite -- --dry-run
```

`scripts/import-sqlite-to-postgres.ts` builds the target schema with the server's own
`initSchema()` rather than a duplicate DDL definition, copies all 22 tables in FK-safe
order (one transaction per table, `ON CONFLICT DO NOTHING` so re-runs are safe), then
resyncs identity sequences with `setval`. That last step matters: rows are inserted
with explicit ids, which does not advance a Postgres identity sequence, so without it
the next `createUser` would collide on the primary key.

`scripts/repair-xp.ts` and `scripts/set-xp.ts` open the SQLite file directly and remain
SQLite-only.
